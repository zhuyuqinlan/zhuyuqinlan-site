## 一条流水线看懂 Java 的前世今生

你写下的每一个 `Hello World`，从一行字符串变成屏幕上的输出，背后其实要经历一场精密的"工业流水线"。

**Java源代码 → 编译 → 字节码 → JVM加载 → 类验证 → 内存分配 → 执行 → GC回收**

这条流水线上的每一道工序，都是 Java 能喊出"一次编写，到处运行"的底气。今天我们就从你敲下第一行代码开始，一步一步把这套流程拆开揉碎。

:::tip
阅读建议：本文配合一个真实的 `Hello.java` 一起看，边读边敲命令，体验感最佳。
:::

---

## 1. 编写 Java 源代码

一切的起点，只是一段纯文本：

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello Java");
    }
}
```

把它保存为 `Hello.java`。此刻它和你在记事本里写的购物清单没有本质区别——**就是一堆字符，JVM 一个字都看不懂**。它需要被"翻译"。

---

## 2. javac 编译：从文本到字节码

执行编译命令：

```bash
javac Hello.java
```

这一步调用的是 **Java Compiler（javac）**，它会把 `Hello.java` 翻译成 `Hello.class`。

:::note
class 文件里装的**不是机器码**，而是 **Java 字节码（Bytecode）**——一种 JVM 能看懂的"中间语言"。
:::

### class 文件结构：除了魔数还藏着什么？

用十六进制打开 `Hello.class`，前 4 个字节是著名的 **CAFEBABE**：

```
0xCA 0xFE 0xBA 0xBE
```

这就是魔数——JVM 加载文件时的第一道关卡，对不上直接拒绝加载。

:::tip[冷知识]
CAFEBABE 的名字来源于 Java 与咖啡的渊源。据说当年 Sun 团队在一家咖啡馆里 brainstorm 出了这个名字。
:::

魔数后面紧跟着**版本号**（次版本号 2 字节 + 主版本号 2 字节），决定了这个 class 文件能在哪个版本的 JVM 上运行。比如 Java 8 对应主版本号 `52`，Java 17 对应 `61`。JDK 新版本可以兼容旧版本编译出来的 class，反过来则不行。

class 文件真正的"重头戏"是**常量池**——它是文件里最大、最复杂的部分，存放着：

- **字面量**：字符串值（`"Hello"`）、final 基本类型常量
- **符号引用**：类名、字段名、方法名等（运行时才会解析成内存地址）

你可以用 `javap -v Hello.class` 把常量池的完整内容"翻"出来看。

### 为什么 Java 不直接编译成机器码？

因为 Java 的野心是 **"一次编写，到处运行"**（Write Once, Run Anywhere）。

如果直接编译成机器码，那生成的就是"Windows 专用"或"Linux 专用"的二进制，换个系统就得重新编译。Java 的解法是：**只编译到"字节码"这一层**，剩下的脏活累活交给各平台的 JVM。

```
同一个 Hello.class
        |
   ┌────┴────┐
   ↓         ↓
Windows JVM   Linux JVM   Mac JVM ...
   ↓         ↓            ↓
各自翻译成各自平台的机器码
```

JVM 就是那个"翻译官"，负责把字节码适配到不同的操作系统和 CPU 架构上。

## 3. 启动 JVM：一个普通的进程

执行运行命令：

```bash
java Hello
```

这条命令的本质，是在操作系统里**启动一个名为 JVM 的进程**。

```
你的程序
    |
    ↓
  JVM 进程
    |
    ↓
  操作系统
    |
    ↓
   硬件
```

:::note
JVM 本质上**也是一个普通程序**，只是它的"职责"是运行 Java 字节码。
- Linux 上：`java` → 加载 `libjvm.so`
- Windows 上：`java.exe` → 加载 `jvm.dll`
:::

说到 `java` 这个命令，顺便提一句你常听说的 **JDK、JRE、JVM** 三者的关系：

```
JDK (Java Development Kit)
├── JRE (Java Runtime Environment)
│   └── JVM (Java Virtual Machine)
└── 开发工具（javac、java、jdb、jstack……）
```

| 概念 | 全称 | 定位 | 包含什么 |
|------|------|------|----------|
| **JVM** | Java Virtual Machine | 运行字节码的"翻译官"，跨平台的核心 | 字节码解释器、JIT 编译器、GC、内存管理等 |
| **JRE** | Java Runtime Environment | 运行 Java 程序的最小环境 | JVM + 核心类库 |
| **JDK** | Java Development Kit | 开发 + 运行的完整工具包 | JRE + javac、jdb、jar 等工具 |

:::tip[一句话记忆]
**开发用 JDK，运行用 JRE，核心是 JVM。** 你敲的 `java Hello` 来自 JDK，真正干活的是 JRE 里的 JVM。
:::

:::note[Java 9+ 模块化变化]
Java 9 引入模块系统（JPMS）后，JRE 不再是 JDK 下一个独立文件夹，而是通过 `jlink` 按需裁剪。但"JDK 包含 JRE，JRE 包含 JVM"这个逻辑关系没有变。
:::

JVM 启动后，第一件事就是去找到 `Hello.class`，准备把它"喂"给类加载器。

## 4. 类加载器：把 class 搬进 JVM

JVM 自己不会到处乱翻文件找 class，它把这个活交给了 **Class Loader（类加载器）**。

Java 默认有三层主要类加载器，形成一条"指挥链"：

```
        JVM
         |
  Bootstrap ClassLoader    ← 加载核心类（java.lang.String、Object 等）
         |
  Platform ClassLoader     ← 加载平台相关扩展类
         |
  Application ClassLoader   ← 加载你应用 classpath 下的类
         |
    你的 Hello.class
```

| 类加载器 | 加载内容 | 实现语言 |
|----------|----------|----------|
| Bootstrap | `java.base` 模块、核心类（String、Object、Integer） | C++ |
| Platform | 平台扩展模块 | Java |
| Application | 你写的类、第三方依赖 | Java |

### 双亲委派机制：防止你"伪造系统类"

:::important
**双亲委派**是面试超高频考点，务必理解。
:::

假设你在项目里手贱写了一个 `java.lang.String`，JVM 会加载你的版本吗？**不会。**

双亲委派的规则是：**收到加载请求时，先委托给父加载器去加载，父加载器搞不定，子加载器才自己动手。**

```
Application ClassLoader  ← "我要加载 java.lang.String"
        |
        ↓  先问爹
Platform ClassLoader      ← "我搞不定，问爹"
        |
        ↓  先问爹
Bootstrap ClassLoader     ← "这是我的活！"
        |
        ↓
找到官方 java.lang.String  ← 加载成功
```

因为 Bootstrap 早就把官方 `String` 加载好了，你的"山寨 String"根本没机会登场。这样就**防止了核心类被篡改**，保证了 Java 平台的安全与稳定。

:::tip[延伸]
当然，双亲委派也是可以被"破坏"的——比如 JDBC 的 SPI 机制（`ServiceLoader`）、Tomcat 的 webapp 隔离、OSGi 热部署，都是通过自定义 ClassLoader 打破这套规则。这部分后续专门笔记再展开。
:::

## 5. 字节码验证：JVM 的安检门

class 加载进来后，JVM 不会立刻执行，而是先做一道"安检"。

**字节码验证器**会检查这个 class 是否"安全合规"：

- 是否存在**非法字节码**（不认识的指令）
- 是否有**栈溢出风险**（操作数栈越界）
- 方法调用时的**类型是否匹配**
- 访问权限是否合法（比如不能 private 方法外部调用）

:::warning
比如 `String s = 123;` 这种类型错误，在 **javac 编译阶段**就会被拒绝。但如果你恶意用十六进制编辑器篡改 class 文件，绕过编译器，JVM 的字节码验证器就是最后一道防线——它会在运行时把这种"带毒"的 class 拦下来。
:::

验证通过，class 才算正式"过海关"，可以进入 JVM 内存了。

## 6. JVM 内存分配：搭好舞台
> 注意计算机组成里面也有堆栈概念，jvm是作为操作系统中一个进程运行，堆栈是他自己分的，例如：jvm规定一个线程占用一个栈，线程私有。

class 进来了，得给它安排地方住。JVM 启动时会划分出一大块运行时数据区，这就是著名的 **JVM 内存结构**：

```
┌─────────────────────────────────────┐
│              JVM Memory              │
├──────────────┬──────────────────────┤
│   方法区      │  类信息、常量池、静态变量 │
├──────────────┼──────────────────────┤
│   堆 (Heap)   │  对象实例、数组        │
├──────────────┴──────────────────────┤
│  线程1        线程2      线程3  ...   │
│ ┌────────┐ ┌────────┐ ┌────────┐    │
│ │ 虚拟机栈 │ │ 虚拟机栈 │ │ 虚拟机栈 │    │
│ ├────────┤ ├────────┤ ├────────┤    │
│ │  PC寄存器│ │  PC寄存器│ │  PC寄存器│    │
│ ├────────┤ ├────────┤ ├────────┤    │
│ │本地方法栈│ │本地方法栈│ │本地方法栈│    │
│ └────────┘ └────────┘ └────────┘    │
└─────────────────────────────────────┘
```

| 区域 | 线程共享？ | 存什么 | 易出问题 |
|------|:--------:|--------|----------|
| 方法区（Metaspace） | 共享 | 类元信息、常量池、静态变量 | Metaspace OOM |
| 堆（Heap） | 共享 | 对象实例、数组 | OOM、GC 主战场 |
| 虚拟机栈 | 私有 | 方法调用栈帧 | StackOverflowError |
| 程序计数器（PC） | 私有 | 当前线程执行的字节码地址 | 唯一不会 OOM 的区域 |
| 本地方法栈 | 私有 | native 方法调用 | StackOverflowError |

:::tip[记忆口诀]
**"两共享，三私有"**：方法区、堆是所有线程共享的；虚拟机栈、PC 寄存器、本地方法栈是每个线程私有的。
:::

## 7. 执行 main：主角登场

舞台搭好，主角登场。JVM 找到那个特殊的入口方法：

```java
public static void main(String[] args)
```

然后创建一条名为 `main` 的线程，正式开始执行。

### 基本类型：直接住栈里

```java
int a = 10;
```

`a` 是基本类型，直接存在当前栈帧（main 方法）里：

```
虚拟机栈
┌──────────────────┐
│  main() 栈帧       │
│  ─────────────    │
│  a = 10           │
└──────────────────┘
```

### 对象：引用在栈，本体在堆

```java
User user = new User();
```

这行代码发生了**两件事**：

**第一步**——堆里开辟空间，创建 `User` 对象：

```
堆 (Heap)
地址 0x1000:
┌──────────────────┐
│  User 对象         │
│  name = null      │
│  age  = 0         │
└──────────────────┘
```

**第二步**——栈里创建引用变量 `user`，保存对象地址 `0x1000`：

```
栈                          堆
┌──────────────┐         ┌──────────────┐
│  user = 0x1000 │ ──────→ │  User 对象     │
└──────────────┘         │  name = null  │
                         │  age  = 0     │
                         └──────────────┘
```

:::note
**变量 `user` 存的是"地址"，不是对象本身。** 这就是为什么 Java 是"值传递"——传的是引用的副本（地址值的拷贝），而不是对象本体。
:::

## 8. 方法调用：栈帧的入栈与出栈

方法调用，本质上就是**栈帧（Stack Frame）的入栈/出栈**。

```java
public void eat() {
    System.out.println("吃饭");
}

public static void main(String[] args) {
    eat();
}
```

执行过程：

```
调用 eat() 前          调用 eat() 中          eat() 执行完
┌──────────┐          ┌──────────┐          ┌──────────┐
│          │          │  eat()   │ ← 栈顶    │          │
├──────────┤          ├──────────┤          ├──────────┤
│  main()  │          │  main()  │          │  main()  │
└──────────┘          └──────────┘          └──────────┘
```

每个栈帧里装着：**局部变量表、操作数栈、动态链接、方法返回地址**。方法执行完，栈帧出栈，局部变量随之销毁——这就是局部变量"方法结束就消失"的原因。

:::warning[经典陷阱]
栈是有限大的。如果方法**无限递归**没有出口，栈帧会不断入栈，最终撑爆虚拟机栈，抛出 `StackOverflowError`。
:::

## 9. 解释执行：字节码怎么变成动作

class 里存的不是机器指令，而是**字节码指令**。

比如 `a + b` 在 Java 源码里就一行，到了字节码层面会被拆成几步：

```
iload   // 把 a 压入操作数栈
iload   // 把 b 压入操作数栈
iadd    // 弹出栈顶两个数相加，结果压栈
istore  // 把结果存回变量
```

JVM 的**解释器**逐条读取这些字节码，"翻译"成当前平台的 CPU 指令执行：

```
字节码  →  解释器  →  CPU 指令  →  执行
```

:::note
解释执行的优点是**启动快、内存省**（不用编译）；缺点是**每次都要翻译**，热点代码会重复"翻译"很多次，效率低。这就引出了下一道工序——JIT。
:::

---

## 10. JIT 编译：把热点代码"焊死"成机器码

JVM 很聪明：它会偷偷观察哪些代码被执行得最频繁（称为**热点代码 Hotspot**，这也是 HotSpot JVM 名字的由来）。

```java
for (int i = 0; i < 10000000; i++) {
    calculate();   // 这个方法被调用了一千万次，是热点！
}
```

一旦某段代码"够热"（默认调用次数阈值约 10000 次），**JIT Compiler（即时编译器）**就会出手，把这段字节码**直接编译成本地机器码**并缓存起来。

```
第一次执行：
.class → 解释器 → CPU

多次执行后（变热）：
.class → JIT 编译 → 机器码（缓存） → CPU 直接跑
```

以后再执行这段代码，**不用解释，直接跑机器码**，速度逼近 C/C++。

### 解释执行 vs JIT 编译

| 执行方式 | 何时用 | 速度 | 启动开销 |
|----------|--------|------|----------|
| 解释执行 | 程序启动初期、冷代码 | 慢 | 几乎无 |
| JIT 编译 | 热点代码 | 快（接近原生） | 有编译开销 |

```text
字节码: iload_1, iload_2, iadd, istore_3
解释器:  翻译 → 执行 → 翻译 → 执行 → 翻译 → 执行 …
```

解释执行的优点是**启动快、内存省**（不用编译）；缺点是**每次都要重新翻译**，热点代码会重复"翻译"很多次，效率低。

### C1 与 C2：分层编译各司其职

现代 HotSpot JVM 默认开启**分层编译（Tiered Compilation）**，用两个编译器配合，兼顾启动速度和峰值性能：

| | C1 (Client Compiler) | C2 (Server Compiler) |
|--|---------------------|---------------------|
| 定位 | 快速编译，低延迟 | 深度优化，高吞吐 |
| 优化程度 | 简单优化（方法内联、部分冗余消除） | 激进优化（循环展开、逃逸分析、向量化） |
| 编译速度 | **快** | 慢 |
| 代码质量 | 一般 | **极高** |
| 触发时机 | 方法调用达到 C1 阈值（约 10000 次） | 代码持续"够热"（OSR 或热点方法） |

编译过程实际上是四级跳：

```text
L0: 解释执行（Profiling：收集分支、类型等运行时信息）
L1: C1 无 profiling 编译（基准性能）
L2: C1 带 profiling 编译（收集更多信息用于 C2）
L3: C2 全优化编译（利用 L0-L2 收集的运行时信息做激进优化）
```

:::tip[GraalVM 的崛起]
从 Java 10 开始，JVM 支持用 Graal 编译器替代 C2（JEP 317）。Graal 是用 Java 写的编译器，支持更激进的优化和 AOT 编译（`jaotc`），在云原生场景下越来越受重视。
:::

:::note[JVM 实际采用"混合模式"]
现代 HotSpot JVM 默认是 **mixed mode**：冷代码用解释器，热代码自动切 JIT。`java -version` 输出里的 `mixed mode` 就是这么来的。你可以用 `-Xint` 强制纯解释、`-Xcomp` 强制纯编译来体验差异。
:::

## 11. GC 垃圾回收：自动清理战场

C/C++ 程序员要手动 `free`/`delete` 释放内存，Java 程序员爽在——**JVM 会自动帮你回收垃圾**。

```java
User user = new User();   // 堆里创建对象
user = null;              // 引用断开，对象成孤儿
```

```
堆
┌──────────────────┐
│  User 对象         │  ← 没有任何变量指向它了
│  (没人要的垃圾)    │
└──────────────────┘
```

GC（Garbage Collector）会通过**可达性分析**：从 GC Roots 出发，顺着引用链找，**能找到的对象是活的，找不到的就是垃圾**，直接回收。

:::note
GC 的核心问题不是"回收什么"，而是"怎么回收得又快又稳"——这就涉及分代收集、标记-复制、标记-整理、G1/ZGC 等算法与收集器，是后续 JVM 专题的重点。
:::

## 12. 程序结束：曲终人散

`main` 方法执行完毕，主线程结束。如果此时没有其他**非守护线程**（比如用户线程）还在跑，JVM 就会退出。

退出时，JVM 释放所有资源：

```
堆内存          ✓ 释放
虚拟机栈        ✓ 释放
方法区/Metaspace ✓ 释放
线程            ✓ 销毁
类信息          ✓ 卸载
文件句柄/网络连接 ✓ 归还 OS
```

一场完整的 Java 程序生命周期，到此谢幕。

```
            Hello.java (纯文本)
                |
                | javac 编译
                ↓
            Hello.class (字节码, CAFEBABE)
                |
                | java 命令
                ↓
            JVM 进程启动
                |
                ↓
        ClassLoader 加载
                |
                ↓
          字节码验证 (安检)
                |
                ↓
        JVM 内存初始化 (方法区/堆/栈/PC/本地方法栈)
                |
                ↓
          创建 main 线程
                |
                ↓
          执行字节码
                |
        ┌───────┴───────┐
        ↓               ↓
    解释器执行       JIT 编译热点 (→ 机器码缓存)
        ↓               ↓
        └───────┬───────┘
                ↓
              CPU 执行
                |
                ↓
         GC 回收无人引用的对象
                |
                ↓
            main 结束 → JVM 退出
```

| **类加载机制** | 双亲委派、打破双亲委派、`<clinit>` 时机 | ★★★★★ |
| **JVM 内存模型** | OOM 定位、调优、分代划分 | ★★★★★ |
| **对象创建全过程** | `new` 指令 → 分配 → 初始化 → `<init>` | ★★★★ |
| **JIT 优化** | 热点探测、C1/C2、逃逸分析、方法内联 | ★★★ |
| **GC 算法与收集器** | 可达性分析、分代、G1/ZGC、调优 | ★★★★★ |
| **线程与栈帧** | 栈帧结构、方法调用、并发可见性 | ★★★★ |
